دستیار هوشمند و گفتگوی آنلاین برای وردپرس با ظاهر شیشه‌ای به سبک iOS، اندیکاتور مغزِ در حال تفکر، ورود اپراتور انسانی و اینباکس پیشخوان — محصول اتحاد وردپرس.

== Description ==

پاسخ‌بان دو حالت نمایش دارد که از یک پنل تنظیمات انتخاب می‌شوند:

**۱) چت آنلاین شیشه‌ای (پیش‌فرض)** — حباب شناور در همهٔ صفحات سایت، پنل شیشه‌ای به سبک آیفون (Liquid Glass)، اندیکاتور «مغز در حال تفکر» هنگام تولید پاسخ، و امکان ورود اپراتور انسانی از اینباکس پیشخوان.

**۲) مغز کیهانی** — همان نمایهٔ سر انسان با شبکهٔ عصبی سیناپسی متحرک به سبک blueprint.

محصول اتحاد وردپرس (etehadwp.com) — اتحاد وردپرس.

ویژگی‌ها:

* چت آنلاین در همهٔ صفحات با ظاهر شیشه‌ای (glassmorphism) و حالت روشن/تاریک خودکار.
* اندیکاتور مغز متحرک هنگام تفکر که با رسیدن پاسخ محو می‌شود.
* پاسخ‌گویی با هوش مصنوعی (GPT / Claude / Gemini) از طریق API گپ‌جی‌پی‌تی (پرداخت ریالی).
* ورود اپراتور انسانی: با نوشتن پاسخ دستی، آن مکالمه از هوش مصنوعی جدا می‌شود.
* اینباکس کامل در پیشخوان با جستجو، نشانگر خوانده‌نشده، و «اپراتور در حال نوشتن…».
* ماندگاری مکالمات در دیتابیس وردپرس (دو جدول اختصاصی).
* ورودی صوتی با Web Speech API و خروجی صوتی با موتور گفتار مرورگر (حالت مغز).
* پاسخ بر اساس محتوای سایت (RAG) به همراه لینک منابع.
* جست‌وجوی معنایی برداری: سؤال‌های هم‌معنی هم به محتوای درست می‌رسند، نه فقط کلمه‌های مشترک.
* ارسال تصویر و فایل در چت، با گیرهٔ کاغذ، کشیدن‌ورهاکردن و Ctrl+V، و نمایش ضمیمه در اینباکس اپراتور.
* دستیار اپراتور: «پیشنهاد پاسخ» و «خلاصهٔ مکالمه» با هوش مصنوعی در اینباکس، با انتخاب لحن.
* آگاهی از ووکامرس: ایندکس محصولات با قیمت و موجودی، و استعلام امن وضعیت سفارش توسط مشتری.
* تیم پشتیبانی: نقش اختصاصی «اپراتور پاسخ‌بان»، واگذاری نوبتی مکالمات، و ساعت کاری.
* ایرانی‌سازی کامل: تقویم شمسی در همه‌جا، اعلان پیامکی (کاوه‌نگار/ملی‌پیامک/SMS.ir) و برندسازی سفید.
* کانال بله: اعلان پیام بازدیدکننده به گروه پشتیبانی، و پاسخ دوطرفه از داخل بله با webhook.
* کلید API فقط روی سرور ذخیره می‌شود و به مرورگر نمی‌رود.
* محدودسازی نرخ درخواست برای جلوگیری از سوءاستفاده.

== Installation ==

1. پوشهٔ `pasokhban` را در `wp-content/plugins/` آپلود کنید.
2. پلاگین را از منوی «پلاگین‌ها» فعال کنید (جداول دیتابیس خودکار ساخته می‌شوند).
3. به منوی «پاسخ‌بان ← تنظیمات» بروید و کلید API گپ‌جی‌پی‌تی و مدل را وارد کنید.
4. حباب چت در گوشهٔ سایت ظاهر می‌شود؛ مکالمات در «پاسخ‌بان ← گفتگوهای آنلاین» ذخیره می‌شوند.
5. برای جاسازی داخل صفحه، شورت‌کد `[pasokhban]` را بگذارید.
6. (اختیاری) برای جست‌وجوی معنایی: تب «دستیار و دانش سایت» ← «جست‌وجوی معنایی (بردار)» را روشن کن، تنظیمات را ذخیره کن و دکمهٔ «ساخت ایندکس» را بزن.
7. (اختیاری) برای ارسال فایل: تب «چت آنلاین» ← «ارسال فایل» را روشن کن و حجم و پسوندهای مجاز را تنظیم کن.

== FAQ ==

= جست‌وجوی معنایی چه فرقی با RAG قبلی دارد؟ =

تا ۱.۸ دستیار فقط نوشته‌هایی را پیدا می‌کرد که **کلمهٔ مشترک** با سؤال داشتند. یعنی «چطور پولم را پس بگیرم؟» به نوشتهٔ «ضمانت‌نامهٔ محصول» نمی‌رسید، چون هیچ کلمهٔ مشترکی ندارند. حالا محتوا یک‌بار به بردار عددی (embedding) تبدیل می‌شود و سؤال با نزدیک‌ترین بردار جور می‌شود.

= چقدر هزینه دارد؟ =

فقط یک‌بار برای ساخت ایندکس، و بعد از آن فقط برای نوشته‌های تازه یا ویرایش‌شده. با `text-embedding-3-small` و ۵۱۲ بعد، هزینهٔ ایندکس یک سایت چندصدصفحه‌ای عملاً ناچیز است. نتیجهٔ هر سؤال هم کش می‌شود، پس سؤال تکراری هیچ هزینهٔ embedding ندارد.

= چقدر کند می‌شود؟ =

جست‌وجو در PHP و خطی است (بدون سرور برداری خارجی). اندازه‌گیری واقعی همین کد با ۵۱۲ بعد: ۵۰۰ تکه ≈ ۲۲ میلی‌ثانیه، ۱۰۰۰ تکه ≈ ۴۵، ۲۰۰۰ تکه ≈ ۹۱، ۴۰۰۰ تکه ≈ ۱۵۹. با ۲۵۶ بعد این عددها تقریباً نصف می‌شوند (۵۰۰ تکه ≈ ۱۲ میلی‌ثانیه). این عددها هزینهٔ PHP است و خواندن بردارها از MySQL واقعی کمی به آن اضافه می‌کند. یک درخواست شبکهٔ embedding هم هست که فقط برای سؤال‌های تازه اتفاق می‌افتد. اگر ایندکست بزرگ شد، ابعاد بردار را روی ۲۵۶ بگذار.

= اگر درگاه API از embedding پشتیبانی نکند چه؟ =

چت مثل قبل با جست‌وجوی کلیدواژه‌ای کار می‌کند. دکمهٔ «آزمایش اتصال» همان اول خطای واقعی را نشان می‌دهد و خطا در همان کارت ثبت می‌ماند. هیچ‌وقت پیام خطا به بازدیدکننده نمی‌رسد.

= ارسال فایل امن است؟ =

چهار لایهٔ محافظت دارد: (۱) فهرست سفید پسوند — نه فهرست سیاه؛ (۲) بررسی MIME واقعی محتوا با `finfo` و مطابقتش با پسوند، پس فایلی که پسوند `.jpg` دارد ولی محتوایش PHP است رد می‌شود؛ (۳) نام فایل هرگز از کاربر گرفته نمی‌شود و یک نام تصادفی ۲۴ کاراکتری جایگزینش می‌شود؛ (۴) پوشهٔ آپلود با `.htaccess`، `web.config` و `index.php` قفل می‌شود.

**SVG عمداً مجاز نیست.** یک فرمت «تصویر» است که می‌تواند JavaScript داشته باشد و در مرورگر اپراتور اجرا شود.

یک نکتهٔ طراحی مهم: کلاینت هرگز URL فایل را به سرور نمی‌فرستد. سرور برای هر آپلود یک **توکن یک‌بارمصرف** می‌دهد و کلاینت فقط توکن را برمی‌گرداند. وگرنه کاربر می‌توانست هر آدرس دلخواهی را به‌عنوان ضمیمه جا بزند و اپراتور رویش کلیک کند.

= 3.1.0 =
* **صفحهٔ «بررسی سلامت»** (تب 🩺 در تنظیمات): ۳۷ بررسی در ۸ گروه که هر مسیر را **با فراخوانی واقعی** می‌آزماید — محیط وردپرس، پایگاه‌داده، هوش مصنوعی، چت و آپلود، اعلان‌ها، ووکامرس، کانال بله، و فایل‌ها.
* هر بررسی زمان پاسخ را اندازه می‌گیرد و در صورت خطا **راهنمای رفع فارسی** می‌دهد (مثلاً: «کلید API رد شد»، «تلگرام فیلتر است، رلهٔ گوگل را تنظیم کنید»، «بله فقط پورت ۴۴۳ و ۸۸ را قبول می‌کند»).
* دکمهٔ «کپی گزارش» یک گزارش متنی می‌سازد که مشتری می‌تواند در تیکت پشتیبانی پیست کند. کلیدهای API در گزارش پوشانده می‌شوند.
* بررسی‌ها یکی‌یکی اجرا می‌شوند تا یک سرویس تایم‌اوت‌شده، کل صفحه را بلوکه نکند و پیشرفت زنده دیده شود.
* **هزینه‌ای نمی‌تراشد**: پیامک واقعی نمی‌فرستد، پیامی به گروه تلگرام یا بله نمی‌دهد، ایمیل آزمایشی ارسال نمی‌کند. برای تلگرام و بله از `getMe` استفاده می‌کند که همان اعتبارسنجی است بدون پیام.
* **رفع باگ**: `Pasokhban_DB::get_or_create_session()` کلید ارائه‌شده را به `create_session()` نمی‌داد و دور می‌ریخت. در نتیجه اگر بازدیدکننده کلیدی معتبر ولی ناموجود می‌فرستاد (بعد از خالی‌شدن جدول، مهاجرت، یا کپی‌گرفتن از سایت آزمایشی) کلید localStorage او بی‌اعتبار می‌شد و درخواست بعدی‌اش نشست *تکراری* می‌ساخت.
* **رفع باگ**: سطر «نسخهٔ ساختار» در جدول وضعیت سیستم روی رشتهٔ ثابت `1.3.0` مقایسه می‌شد؛ از وقتی ساختار به ۱.۸.۰ رسیده بود این سطر برای همه ⚠ نشان می‌داد حتی وقتی همه‌چیز سالم بود.
* **رفع**: متغیر سراسری `window.ETEHADYAR` از رنیم ۳.۰.۰ جا مانده بود. حالا `window.PASOKHBAN` تزریق می‌شود و نام قدیمی به‌عنوان پشتیبان می‌ماند تا اگر هاست نسخهٔ کهنهٔ JS را کش کرده باشد ویجت مغز کیهانی از کار نیفتد.
* افزودن `wp_date()`, `wp_timezone()`, `is_email()` و `wp_check_filetype_and_ext()` به هارنس تست.

= 2.9.1 =
* رفع مهم: اندازهٔ پنل چت از سمت کاربر به‌هم ریخته بود. در ۲.۸.۰ یک بلوک `@supports (height: 100dvh)` **بدون** media query اضافه شده بود که ارتفاع پنل را روی `92dvh` می‌گذاشت. چون JavaScript کلاس `.sheet` را بر اساس «تنظیم» اضافه می‌کند نه «عرض صفحه»، آن بلوک در **دسکتاپ** هم اعمال می‌شد و پنل تقریباً تمام‌صفحه می‌شد.
* رفع: ارتفاع پنل در موبایل حالا `min(78vh, 620px, calc(100vh - فاصلهٔ پایین - حباب - 36px))` است. نسخهٔ قبلی فقط `min(78dvh, 620px)` داشت و قید «منهای حباب» را باطل می‌کرد، پس در صفحه‌های کوتاه پنل از viewport بیرون می‌زد و روی حباب شناور می‌افتاد.
* رفع: `max-height` هم قید viewport گرفت.
* رفع: عرض پنل در موبایل `calc(100vw - 2 * var(--psb-off-side))` شد تا با فاصلهٔ واقعی کنار هم‌خوان باشد، نه عدد ثابت ۲۴ پیکسل.
* تست: ۱۹ تست تازه برای اندازهٔ پنل، شامل تحلیل ایستا که هیچ قانون پنلی بیرون media query نشت نکند. تأیید شد که این تست‌ها با CSS خرابِ ۲.۸.۰ قرمز می‌شوند.

* رفع ریشه‌ای: اگر dbDelta بی‌صدا شکست می‌خورد (مثلاً کاربر MySQL حق CREATE TABLE نداشت)، گزینهٔ نسخهٔ ساختار ثبت می‌شد و پلاگین تا ابد فکر می‌کرد جدول‌ها هستند. در نتیجه هیچ گفتگویی ذخیره نمی‌شد و لیست اینباکس خالی می‌ماند بدون هیچ خطایی.
* جدید: install() حالا وجود واقعی جدول‌ها را بررسی می‌کند و در صورت شکست WP_Error با علت دقیق MySQL برمی‌گرداند.
* جدید: نوار تشخیصی اینباکس حالا شامل آزمون زندهٔ نوشتن/خواندن/حذف، وضعیت مسیرهای REST و آخرین خطای MySQL است.
* جدید: دکمهٔ «ساخت/تعمیر جدول‌ها» در اینباکس.
* تغییر: فیلتر پیش‌فرض اینباکس از «باز» به «همه» — تا هیچ مکالمه‌ای پشت فیلتر پنهان نماند.
* رفع: علت خطای MySQL قبل از پاک‌شدن last_error گرفته می‌شود.
